# Research working documents and publication history

The canonical Source Artifact remains immutable. Attach each cleaned working-document revision as a supporting `research_notes` Artifact on its Source. Set a stable `metadata.document_key` and point `supersedes_artifact_id` and `metadata.predecessor_artifact_id` at the prior working revision. List Artifacts newest first, select the latest entry for that key, and retain every earlier version. This does not promote a working note into the Source's canonical evidence.

Authenticated `context_apply` callers may use this append path on an active protected Source. The server accepts the append only for `research_notes`, requires a nonempty document key, and permits supersession only within the same Source and key. The protected flag, Source fields, and canonical evidence pointer remain unchanged; all other protected Object mutations remain forbidden.

Attach publication history to the originating Note as `publication_receipt` Artifacts. Put a complete JSON snapshot in `content`: destination, status (`draft` or `published`), actual copy, provider/post identity, URL if known, media references, occurrence time, originating Note revision, related Note IDs and candidate digest. Metadata may repeat searchable fields. A draft does not prove a live post. A published receipt requires provider readback or explicit user confirmation. For an edit, append a successor with `supersedes_artifact_id`; a new share gets a distinct provider identity and Artifact. Use a stable idempotency key and reconcile uncertain writes before retrying. Artifact writes advance the Object revision but do not edit the Note's content or intent.

This is a generic Artifact convention. Provider credentials and editorial decisions belong to the calling overlay.

## Supporting research visuals

PNG and JPEG `research_visual` Artifacts are attached to an existing Source and stored as immutable binary payloads in PostgreSQL. They do not alter the canonical captured Artifact or indexed text. The agent listener accepts `POST /api/v2/sources/{source_id}/visual-artifacts` with raw image bytes, `Content-Type`, `Idempotency-Key`, and `X-Artifact-Title`, `X-Artifact-Description`, `X-Artifact-Document-Key`, and `X-Artifact-Expected-Revision` headers. Optional `X-Artifact-Supersedes-Id` identifies the preceding visual with the same key; `X-Artifact-Method` records the actual generation method. The endpoint verifies full decoding, MIME, 20 MiB encoded and 24 megapixel decoded limits, Source revision, predecessor identity, actor and thread attribution, and the idempotency request. A repeated identical request returns the same Artifact; different content or metadata under the same key conflicts.

The response includes Artifact metadata and `/sources/{source_id}/artifacts/{artifact_id}`. `GET /api/v2/artifacts/{artifact_id}/binary` reads the bytes through the agent or human listener. `?download=true` uses an attachment disposition. Binary responses use `private, no-store` and `nosniff`. The browser groups visual revisions by `metadata.document_key` and opens a wide viewer. The packaged `context_visual` command takes a local file, resolves the current Source revision, uploads it with the existing agent token and thread identity, and verifies byte readback. It does not ask the server to read a client pathname. Link the viewer path from a working research document or Note when useful.

The bounded PostgreSQL v1 design keeps upload, Artifact/event and bytes in one transaction and within the existing database backup boundary. Monitor database growth; a future object-store migration needs its own backup and authority design. No new text-only data migration is required.
