# Open every Object in its complete type-specific detail view

## Outcome
Opening an Object anywhere in Context shows the full detail appropriate to its canonical kind. A Note always exposes its body; a Task always exposes its workflow and brief. Different entry points must not show incomplete versions of the same record.

## Repository scope
Implementation owner: bradwmorris/centaur-context, [Issue #128](https://github.com/bradwmorris/centaur-context/issues/128). Planning-only RD and linked repository Issue; execution starts separately. Expected changes are web routing, detail composition, shared identity links and regression tests. A minimal authenticated read API extension is permitted only if existing Entity/Memory subtype fields cannot be retrieved through a suitable existing UI API. No schema migration or new product fields. No other repository implementation is required; flag any deployment dependency before expanding scope. Public artifacts use synthetic examples only.

## Requirements
- One canonical detail route per current Object kind: tasks, notes, sources, themes, entities, memories, users and chats. Shared components are encouraged; separate component files are not a requirement.
- All ordinary Object-opening interactions resolve to that complete type-specific view: Objects and typed collection rows, search/filter results, Related Objects, graph nodes and inspectors, Connection endpoints, Object ID pills, activity references, Task/Run references, artifact back links and registered UI views.
- Preserve /objects/:id as a compatible entry route. Resolve the actual record kind independently of the loaded collection (including records absent from the current list), then replace history with the correct typed route. Correct mismatched typed routes using the same authoritative resolver. Preserve appropriate query/hash state and avoid redirect loops or extra Back steps.
- Existing /objects/:id/artifacts/:artifactId and /objects/:id/working/:key links must continue to open the exact artifact or working document, not redirect to a parent detail page. Parent navigation opens the full type-specific detail.
- Notes expose body, format and intent; Tasks expose brief, owner/due date, status, priority, blockers and Issue; Sources retain source metadata and artifacts; Themes retain existing membership behavior; Chats retain messages and Users retain identities. Entities expose existing entity_kind and image where present; Memories expose happened_at. Reuse current subtype schemas; do not invent entity profile or memory editing features.
- All detail views retain shared title/description, identity, provenance, connections, activity and existing authorized editing. Do not lose generic fields when switching to typed views. Preserve protected/read-only restrictions and unsaved-edit navigation guards.
- Native link behavior must work: copy/open link, modifier-click/new tab, keyboard activation, direct load/refresh, browser Back/Forward. Buttons within a clickable row (copy/edit/select) must not accidentally open the record.
- Keep explicit Schema table/row inspection routes, Connection details, Runs and Evals distinct: these are not Object kinds. An Object reference within them still opens its typed detail. Unknown future kinds get a safe generic fallback; missing, inaccessible or inconsistent records show an honest error, not a misleading empty detail page.
- Excludes research record changes, automatic connection creation, schema consolidation, a general UI redesign, new permissions and new external integrations.

## Approach
Current references: web/src/App.tsx chooses NoteDetail, TaskDetail, SourceDetail and ThemeDetail based on the URL section; ObjectDetail omits their subtype content but conditionally adds ChatTranscript and UserIdentityPanel. RelatedObjectRow hardcodes the objects section. web/src/routing.ts objectPath always targets /objects; web/src/ObjectIdentity.tsx, ConnectionGraph.tsx and SchemaWorkspace.tsx consume it. Existing tests in routing.test.ts, ObjectIdentity.test.tsx, ConnectionGraph.test.tsx, App.test.tsx and ArtifactWorkspace.test.tsx assert generic links. Inspect registered/overlay view contracts and remaining call sites during execution.
Centralize kind-to-route mapping and canonical resolution rather than scattering switches or relying on collection membership. Known-kind links may use the typed route immediately; ID-only links can use the compatible resolver. Reuse a shared metadata shell with kind-specific content so generic information and editing remain available. Check existing authenticated APIs for Entity/Memory subtype retrieval; extend read responses minimally only if necessary, without changing existing field meanings or exposing private internals. Preserve loading cancellation and revision/conflict behavior. Do not rewrite stored URLs or duplicate records.
